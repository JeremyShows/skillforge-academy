## Contributor governance controls and PR #19 review

The earlier audit snapshot recorded a default-branch ruleset requiring a pull request, one approving review, approval of the latest push by someone other than its author, stale-approval dismissal, and code-owner approval. On the latest follow-up check, PR #19 was open at head `17329cc4e531da99569ce99e2e6579884afff5dd`, with `REVIEW_REQUIRED`, `BLOCKED` merge state, mergeable changes, zero submitted reviews, zero review requests, and no reported checks. Current ruleset verification is incomplete: repository metadata exposes an active no-delete ruleset, the classic branch-protection endpoint reports no protection, and organization ruleset metadata is unavailable through the current credential. Do not merge until an owner confirms the currently applicable review requirements.

The initial `.github/CODEOWNERS` file is introduced by PR #19, not present on its base branch. GitHub uses the base branch's CODEOWNERS file for review requests, so no code-owner request can be generated for PR #19 itself. After merge, the file would cover the listed paths. The Maintainers team currently has one member, the PR author, so no non-author maintainer is available to satisfy code-owner review on future maintainer-authored protected-path PRs while invitations remain blocked. This is a P2 governance availability blocker, not a personal-data exposure in the PR diff.

A read-only author scan of the exact follow-up PR diff found no email-like strings or local Windows user/project paths in added lines. This is not an independent review and is not GitHub approval. The prior exact-head self-review is also not independent. Formal non-author approval remains outstanding, the applicable ruleset must be reverified, and the latest push has no review. RepoPact validates record schemas and evidence but does not authenticate record authors. A dedicated CI identity check would be required if policy must reject a non-maintainer's proposed work-item change before maintainer review; that CI control is not configured.

## Readiness and blockers

Contributor onboarding is **BLOCKED** until all of the following are resolved:

1. Verify effective access with an explicitly authorized disposable identity or supported permission-check mechanism. None was available; the owner account was not used as a substitute, and no contributor was invited.
2. Obtain sufficient read-only access to organization Actions-policy and secret-sharing metadata and personal package metadata, or have the owner verify these boundaries without exposing secret values or course contents.
3. Have the release owner privately classify the two custom-domain contacts. Until ownership is confirmed, use role-based contacts in future release builds; changing existing release assets remains separately authorized work.
4. Obtain owner authorization for targeted remediation of the historical machine-profile path in PR #14 and the private checkout markers in two branch tips and PRs #16/#18. No history was rewritten, branch deleted, PR removed, or evidence deleted.
5. Have an owner reverify the currently applicable review ruleset through an authorized metadata view. The PR reports `REVIEW_REQUIRED`; the current credential cannot inspect organization ruleset metadata.
6. Obtain independent technical review and formal non-author GitHub approval after the final push. No eligible non-author reviewer is available; the sole organization member and direct collaborator is the PR author.
7. Establish an authorized second maintainer before relying on CODEOWNERS for future owner-authored protected-path PRs. Invitations remain blocked.
8. Before contributor invitations are reopened, decide whether to restrict repository creation, outside invitations, and require organization two-factor authentication; those settings were not changed in this reassessment.

This audit does not establish access by impersonating a new member, and it does not claim that written policy alone enforces work-item governance.
